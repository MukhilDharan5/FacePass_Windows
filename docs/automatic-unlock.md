# Automatic face verification and interaction to unlock

Select **Authentication → Activation mode → Automatic → Save preferences** in the installed Settings app. The existing face enrollment and unlock backend must already be configured. After a service update/restart, unlock once with Windows PIN/password. Automatic mode then starts one bounded scan when that account's console session locks, or resumes while Windows reports it locked. It does not require selecting Sign-in options → FacePass. Manual mode still starts recognition on FacePass selection; Scan again allows an explicit retry in either mode. Off cancels scanning and revokes approvals.

The service owns automatic activation. It uses the same recognition policy, encrypted credential store, session checks, ten-second one-use approval, and authentication backend as manual unlock. A trusted LogonUI status poll can also start the attempt if capture was busy when the lock event arrived. A poll arriving before the lock event waits for eligibility instead of making an unsuccessful Recognize request. There is one automatic attempt per lock/resume, so a failed, timed-out or cancelled scan does not repeatedly take over the camera. Select FacePass → Scan again or use Windows PIN/password after failure.

After recognition, Windows stays locked. FacePass displays **Face verified. Press Space or Enter, or interact with the lock screen to continue.** on its tile. Keyboard or mouse activity after verification allows the provider to request sign-in. Input from before verification, a tile becoming selected, and waiting without input do not submit credentials. The existing approval lasts ten seconds; after it expires, select **Scan again** or use Windows PIN/password.

The provider observes the service from its provider-level Advise/user-enumeration lifecycle, independently of SetSelected. It stays subscribed after failure/approval expiry while advised, with slower idle polling, so resume works even if Windows retains the same provider object. Until both a live SID/session-bound approval and subsequent interaction are present, GetCredentialCount returns CREDENTIAL_PROVIDER_NO_DEFAULT and FALSE, SetSelected returns FALSE for automatic sign-in, and GetSerialization returns no credential. After both conditions it calls CredentialsChanged once for that approval and supplies its credential index and TRUE for pbAutoLogonWithDefault. GetSerialization then follows the existing password-backed Negotiate or legacy backend path. Credential-level UnAdvise and unchanged user enumeration preserve the scan or waiting approval during UI re-enumeration.

Interaction uses the session-specific timestamp from [GetLastInputInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo), sampled after the provider observes each new face approval. [GetUserObjectInformationW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getuserobjectinformationw) confirms that the provider's Winlogon desktop is receiving input. Fresh input timestamps must fall after arming and no later than the current uptime; unsigned arithmetic handles the uptime counter wrapping. Missing input information or an inactive desktop prevents submission. Each new approval needs another interaction; confirmation is cleared on cancellation, consumption, expiry, and desktop inactivity. No key contents, mouse coordinates, input hooks or injected input are used. This is a user-presence cue, not a second authentication factor.

## What Windows controls

[CredentialsChanged](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/nf-credentialprovider-icredentialproviderevents-credentialschanged) requests credential re-enumeration; it does not force Windows to select this provider. [GetCredentialCount](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/nf-credentialprovider-icredentialprovider-getcredentialcount) documents an auto-logon default that asks LogonUI to call GetSerialization, including precedence over an existing default without auto-logon. Windows still arbitrates providers, policy and UI state. [SetSelected](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/nf-credentialprovider-icredentialprovidercredential-setselected) documents that Windows can require a sign-in button instead of honoring automatic logon.

The implementation requests submission only after recognition and subsequent lock-screen interaction. Windows retains control of provider selection, curtain dismissal, secure attention and final submission. Native PIN/password providers remain available. If Windows retains another provider or requires its sign-in button, select FacePass and use Unlock while the approval is live, or Scan again after expiry.

**The exact physical Space/Enter/mouse and lock-curtain behavior still needs a live laptop test.** Automated tests exercise the production provider with simulated input timing and desktop state. Face recognition alone intentionally leaves Windows locked. Existing restrictions remain: an already authenticated console session, one native authentication after service startup, supported configured account/backend, and no RDP or boot-sign-in support.

## Camera and session lifecycle

The supervised capture worker releases the webcam before the service publishes a successful approval. Cancellation, Off, scan timeout, provider-level UnAdvise/destruction, leaving a selected FacePass tile, session unlock/desktop return, disconnect/logoff and suspend request cancellation and revoke approval. Cancellation is bounded by the existing capture supervisor, including termination of a blocked camera worker. A late queued provider update cannot restore a cancelled ticket. Leaving FacePass cancels the current attempt but retains status observation for a future lock/resume if Windows keeps the provider advised. Deselecting a tile that was never selected does not interrupt background Automatic recognition while PIN/password is active.

Resume queries the documented WTS session lock flag. It preserves already observed native-session provenance but never creates it. Duplicate lock/resume notifications do not restart capture. Provider cancellation carries the lock/resume episode it observed, so a delayed cancellation from an old screen cannot stop a newer scan for the same SID/session. Disconnect/logoff cleanup runs even if Windows already switched the active console, so another user cannot inherit the camera job or approval.

Provider, service, Settings and CLI use IPC protocol version 5 and must be updated together. Configuration/template/password storage formats are unchanged.

## Verification on Windows

1. Update all packaged binaries, unlock once with native PIN/password, then save Automatic. Leave PIN/password selected and lock. Confirm the webcam starts without choosing FacePass. Keep the keyboard and mouse still after verification: Windows must remain locked. Then press Space or Enter, or interact with the lock screen within ten seconds. Check that Windows proceeds only after that interaction. Repeat with FacePass selected and in Manual mode.
2. Inspect FacePass provider stage messages with scripts/capture-provider-events.ps1: face verified and awaiting lock-screen interaction; interaction confirmed after face verification; interaction-confirmed sign-in requested; credentials enumerated with automatic=1; serialization requested; Windows result. Before input, there must be no sign-in request or credential submission. Wait past ten seconds and confirm that input cannot reuse the expired approval. A recognition result or CredentialsChanged S_OK alone is not proof of unlock.
3. Test an unknown face and timeout while entering native PIN/password. Confirm the camera stops on desktop return. Select FacePass, then switch to PIN/password to cancel. Test Off and Manual separately.
4. Test sleep/resume, disconnecting the camera, fast user switching and sign-out. Check that no approval crosses sessions, no cancelled scan submits later, and no camera worker remains after sign-in.

The automatic lifecycle suite uses the actual provider/controller code with test-only OS/IPC/capture seams and an isolated encrypted fixture store. Production binaries contain no test overrides. The existing real capture-supervisor cancellation, model, authentication, storage, Settings and IPC tests remain part of validation.
